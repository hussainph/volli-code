A Linux runner is a box you own — a server, a home machine, a VM — that runs
Sessions while your Mac is closed. You add it from the app: **Settings →
Runners → Add a runner** makes a one-time token and the command that uses it.
You paste the command on the box, and the box does the rest.

Nothing on the box needs a Volli account, a browser or a window. It links
itself with the token, installs as a service, and appears in **Settings →
Runners** as **Online**.

<Aside type="note">
  **Settings → Runners** appears in a Volli Cloud launch. A signed-out local
  launch has no runners.
</Aside>

## Before you start

| Requirement | Detail |
| --- | --- |
| Linux | x86-64 or arm64, glibc 2.31 or newer (Ubuntu 20.04+, Debian 11+, Fedora, RHEL 9+) |
| Disk | 1 GiB free where the runner is installed |
| systemd | Used for the service. Without it the install finishes but starts nothing, and you run `volli-runner run` yourself |
| Git | 2.31 or newer, for the Sessions that clone and push. The installer never installs packages: it prints your distribution's install command instead |
| Network | Outbound HTTPS and WebSocket only. See [Runners](/runners/#network) for the destinations and the ports |

musl systems (Alpine) are not supported, and the installer refuses them with a
one-line reason rather than installing something that cannot run.

## Install it from the app

1. In Volli, open **Settings → Runners** and select **Add a runner**.
2. Type a name — this is how the box appears in the composer — and copy the
   command.
3. Run it on the box, in a shell. It needs `sudo` for a system install; a user
   install needs none.

The command looks like this. The token is single-use and expires an hour
after the sheet makes it, so a copy left in shell history is harmless once it
has been used:

```sh
curl -fsSL https://github.com/hussainph/volli-code/releases/latest/download/volli-runner-install.sh \
  | sh -s -- --token vrt_… --name 'hetzner-1' --user
```

The command **Copy command** gives you the same script pinned to your app's
version, so the box installs exactly the build you are running. Either form
takes the same flags. The sheet offers three variants:

| Variant | What it does |
| --- | --- |
| User install | Installs under your own login, and Sessions run as you |
| Environment variable | The same user install, with the token in `VOLLI_RUNNER_TOKEN` instead of an argument, so it stays out of the process list |
| System install (sudo) | Installs a `volli` service account, and Sessions run as that unprivileged user |

Choose the system install for a dedicated server, and the user install on a
machine you share. `--user` is refused as root: agents never run as root.

### Without a token

If the token has expired, or you would rather approve the box in the app, run
the link on its own:

```sh
volli-runner link
```

It prints a short code. Enter it in **Settings → Runners → Link a runner**,
read the **Machine**, **System** and **IP address** it reports, then select
**Approve runner**. The code waits ten minutes, and only approve a machine
you own: the reported name and address are hints, not proof of identity. A
device code takes its name from what you type in the app, so `--name` is only
for a token.

## What the install does

The script downloads the release for this machine, checks its SHA-256 against
the release manifest, proves the build runs here (natives and Code Mode), and
hands over to `volli-runner install`, which:

- unpacks the release beside any earlier one and moves `current` to it;
- creates the service account and directories (system install) or uses yours;
- installs and starts the systemd service, enabled at boot;
- links the box with the token and waits for the deployment to accept it.

A second run changes nothing and finishes an interrupted one.

| What | System install | User install |
| --- | --- | --- |
| Releases | `/opt/volli-runner/releases/` | `~/.local/share/volli-runner/releases/` |
| Command | `/usr/local/bin/volli-runner` | `~/.local/bin/volli-runner` |
| Data | `/var/lib/volli-runner` | `~/.local/state/volli-runner` |
| Link and keys | `/etc/volli-runner` | `~/.config/volli-runner` |
| Service | `/etc/systemd/system/volli-runner.service` | `~/.config/systemd/user/volli-runner.service` |

The data directory holds the working copies and the runner's machine state.
The link and its keys live in the config directory, so a copy of the data
directory never carries the credential. In a system install the `volli`
account's home is the data directory, so its `~/.git-credentials` and git
config are there too.

A user install keeps running after you log out only if lingering is enabled
for your account (`loginctl enable-linger`). Without it the installer warns,
and the runner stops when your session ends.

## Sign in a model

Sessions on the box need a model provider, signed in **on the box**. The
runner reports which providers it can serve, and the composer offers only
those models for that runner.

```sh
volli-runner login anthropic --api-key      # paste the key at the prompt
volli-runner login --status                 # what this runner can serve
volli-runner logout anthropic
```

Run it with `sudo` on a system install: the sign-in belongs to the service
account, and the command writes it there.

Without `--api-key`, `login` walks the provider's own sign-in in the
terminal: it prints a URL to open, and a code to paste back. Over SSH, use the
paste-the-code option, or forward the provider's callback port first
(`ssh -L 1455:127.0.0.1:1455 box`) and open the URL on your Mac.

Do not copy your Mac's `~/.pi/agent/auth.json` to the box: both machines would
then refresh one grant and sign each other out. Make a separate sign-in on the
box.

An API key exported in the service's environment is not a sign-in. Only what
`volli-runner login` stores is reported, so use the command even when the key
is already on the box.

## Git

Sessions commit and push as the runner's own account. When your Volli Cloud
account has a GitHub connection, the runner asks Volli Cloud for a short-lived
token per Session and keeps nothing on disk.

Without that connection, give the box its own credentials once, **before** it
clones anything: a private repository asks for credentials the moment a clone
starts, and nobody can answer a prompt the agent hits. A deploy key with write
access is the narrowest option; a fine-grained token limited to that one
repository works too.

```sh
sudo -u volli -H install -d -m 700 /var/lib/volli-runner/.ssh
sudo -u volli -H ssh-keygen -t ed25519 -N "" -C "volli@hetzner-1" \
  -f /var/lib/volli-runner/.ssh/id_ed25519
sudo cat /var/lib/volli-runner/.ssh/id_ed25519.pub      # add this as a deploy key with write access
sudo -u volli -H git config --global user.name "Volli on hetzner-1"
sudo -u volli -H git config --global user.email "you+volli@example.com"
```

Keep the credential out of the remote URL: a URL is printed in errors and
copied into every working copy's config. A token goes in the runner account's
`~/.git-credentials` (in a system install, `/var/lib/volli-runner`), never in
the clone command.

## Check it

```sh
volli-runner status        # one JSON report; exit 0 serving, 1 refusing, 3 not serving
volli-runner doctor        # every check, with the one command that fixes it
volli-runner logs -f       # the runner's log, as it happens
```

`doctor` checks git, disk, systemd, the deployment, the git hosts, the model
providers you signed in, and the browser that a runner does not install. A
failure names the exact fix; nothing on the box needs to be guessed at.

On a system install, run these with `sudo` so they read the runner's own
directories.

In the app, the runner's row shows its state and version. From the composer,
pick it for a new Session, or let Volli choose it: an online runner that is
always on and plugged in comes first.

## Updates

A runner updates itself. When the release channel names a newer version and
the box is idle, it stages the release, verifies it, drains, and restarts on
the new one; if it does not come back online, it rolls back and reports what
happened, so a bad release cannot strand a box.

- **Manual.** `volli-runner update` applies the release the deployment asks
  for, now.
- **Needs an update.** A runner below the oldest version the deployment
  accepts shows **Needs an update** in **Settings → Runners** and in the
  composer, and takes no new Sessions until it updates. An update cannot be
  declined past that floor.
- **Channel.** `--channel canary` at install follows prereleases; the default,
  `--channel stable`, follows stable releases. An update never moves a runner
  to an older version.
- **Version.** The runner's row shows the version it reports.

## Remove it

```sh
sudo volli-runner uninstall              # keeps the data directory
sudo volli-runner uninstall --purge      # also removes working copies and the account
```

Uninstall unlinks the runner, stops and removes the service and the release,
and leaves the data directory alone unless you pass `--purge`. With
`--purge` it lists working copies that hold uncommitted or unpushed work and
asks before removing them; `--yes` skips the question.

Removing a runner in **Settings → Runners** is the other direction: it revokes
the runner, which stops claiming work at its next token refresh and stays up
and idle, keeping every working copy. `volli-runner unlink` forgets the link
on the box alone, and refuses while the runner is running.

## If something is wrong

| What you see | What to check |
| --- | --- |
| **Waiting for hetzner-1** in the composer | The box is asleep, stopped or offline. `systemctl status volli-runner`, then `volli-runner status` |
| **Needs an update** | `volli-runner update`, or wait for an idle automatic update |
| The runner vanished from Settings | It was removed there, which revokes it. Forget the old link on the box (`volli-runner unlink`), then link it again (`volli-runner link`) |
| `volli-runner status` exits 3 | Not serving: the output names the reason. `volli-runner logs` has the last lines |
| No model in the composer for this box | Sign in on the box: `volli-runner login --status` shows what it can serve |
| A Session's push failed | The box has no credential for that remote; see Git above |
