**Configure → Authority** sets the policy for a project’s Sessions. An
**attachment** is the live connection a Session runs on, and it pins the policy
when it opens. A change in Configure applies when a new attachment is created,
not to one already running. Relaunching the app replays an existing
attachment’s recorded policy. Volli stores the policy with its project data,
not in a repository configuration file.

## Choose a rule-enforcement posture

The **Rule enforcement** setting has three postures:

| Posture | Effect |
| --- | --- |
| **Off** | Creates no Authority Snapshot and runs no rule checks. |
| **Observe** | The default. Saves the policy for the attachment and allows calls; it does not record individual allowed or refused calls. |
| **Enforce** | Checks calls against Volli’s built-in rules and blocks calls those rules deny. |

In **Enforce**, the default fallback asks you once a Session reaches **3 denials
in a row** or **20 denials total**. You can change either threshold. Only denials
from rules that allow an override can be allowed; other rule violations stay
blocked.

The rules read files the same way a Scoped Session's sandbox does. A Session
can read anywhere on your Mac except the secrets below, and writes only inside
its workspace and the writable roots. Reading a secret is never allowed, even
with your approval.

## Contain a project’s Sessions

**Containment** decides whether a Session’s tools run inside a sandbox:

| Containment | Effect |
| --- | --- |
| **Off** | The default. Shell commands run as your macOS user, with network access. |
| **Scoped** | Shell commands run in a macOS sandbox, and the file tools follow the same policy. Commands have no network access. |

A Scoped Session can read any file except these secrets:

- credential stores: `~/.ssh`, `~/.aws`, `~/.config`, `~/.pi`, `~/.gnupg`, `~/.docker`, `~/.kube`, and other agent tools’ sign-in files
- your home folder’s top-level dotfiles, such as `~/.zshrc`, `~/.netrc` and `~/.gitconfig`
- `~/Library/Keychains`, `~/Library/Application Support` and other app data folders
- other users’ home folders
- Volli’s own data: its database, MCP credentials, backups and other Sessions’ saved output. A Session can still read its own saved tool output.

It can write only in its workspace, in the Git directory a ticket worktree
commits to, and in the **Writable roots** you list. In every one of these
locations, Git hooks, Git config, `.gitmodules` and `.volli/` stay read-only.
In a Scoped Session, editor and agent configuration such as `.vscode/`, `.mcp.json`
and shell profiles is read-only as well. Background shells run inside the same
sandbox.

A Scoped Session has no network access, so commands such as `pnpm install`,
`git fetch` and `git push` fail inside it. Run those commands yourself, or
keep containment **Off** for projects that need them. Containment needs a pinned policy, so it has no effect when
**Rule enforcement** is **Off**.

## Understand the other controls

**Decision mode — not active yet** stores whether the policy names **Ask me** or
**Classifier** as the judge for calls the rules cannot settle. Volli does not
use this setting yet to decide calls, and **Classifier** is unavailable until a
classifier is configured.

The **can read** rows control how much of a Session’s transcript each kind of
caller can read. The inherited choices are:

| Caller | Default access |
| --- | --- |
| **You** | Any transcript in the project |
| **An authenticated session** | Its own transcript |
| **An unauthenticated caller** | No transcripts |

## Know the enforcement boundary

**Enforce** is a rule gate, not a sandbox. With containment **Off**, a
Session’s tools still run with the authority of the account running Volli, and
the built-in rules do not isolate commands from every possible side effect. The
rules can read a command’s file arguments, but not a path hidden in a variable or
a script. Use **Scoped** containment when you need the operating system to
enforce the boundary.
