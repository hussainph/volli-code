# Volli

A local-first macOS workspace for planning and running coding sessions, built with Electron, React, and TypeScript. The app combines a task board, isolated ticket worktrees, durable local history, Pi-backed structured chat, and embedded terminal harnesses. Structured execution uses one Agent Runtime; external and bring-your-own TUI harnesses are manual terminal companions, not structured execution surfaces.

`CONTEXT.md` is the canonical domain glossary and `docs/DESIGN.md` is the living visual language. The code and tests are authoritative for current behavior. Do not infer implemented behavior from a contract or glossary entry alone.

## Structure

- `apps/desktop/src/main/` — Electron main host: composes `@volli/host-core`, Pi runtime hosting, the terminal IPC adapter, the `volli` CLI socket startup and app-quit adapter (`agent-socket-quit.ts`), notifications and Electron adapters. **The only place Electron APIs run.**
- `apps/desktop/src/preload/` — the typed `contextBridge` API; the only door between renderer and main. Thin and explicit.
- `apps/desktop/src/renderer/` — React UI + Zustand stores. UI state projects durable main-process state plus ephemeral view state. **No Node imports.**
- `packages/shared/` (`@volli/shared`) — pure, unit-tested domain code (models, ticket rules, event types, Session semantics, branch/slug rules) plus the Agent Runtime port and its `RuntimeObservation` vocabulary, which live here so `@volli/session-engine` can name the type it holds without taking a Node dependency. **No Electron/Node/DOM imports.**
- `packages/session-engine/` (`@volli/session-engine`) — plain TypeScript Session commands, durable projections, temporary native-executor migration contracts, the translation from runtime observations into durable Session facts, committed streams, and AI SDK transcript vocabulary. **No transport/Node APIs.**
- `packages/session-rpc/` (`@volli/session-rpc`) — thin tRPC Session edge plus sanitized diagnostics.
- `packages/host-core/` (`@volli/host-core`) — the host's services composed without Electron: `createHostCore(ports, options)`, the ports a host answers (`src/ports`: event bus, addressed client event sink, attention delivery, power, client capabilities, trash, secret-key), the SQLite open/migrations/repos (`src/db`) and the transaction-ownership guard. Worktrees/git/change sets, project roots, blob/ticket commands, Session/runtime wiring (including Pi attachment assembly), background shells, the Session secret service, login PATH adoption, observability, MCP, Code Mode, Web Access, decisions, model sign-in, Automations, the one handler map every door projects for catalog commands (`src/handlers`, VC-668), verb dispatch, the agent Unix socket, the terminal (node-pty) supervisor (`src/pty`), and the agent browser's engine-agnostic half (`src/browser`: the `BrowserBackend` seam, shared tab registry, CDP controller and agent port) also live here. Backup/restore, retention, database recovery, orphan scanning and process maintenance live here too (`host.maintenance`); desktop retains their IPC doors and app quit gates, while host shutdown drains Sessions/MCP/observability under the unchanged deadline. Electron main calls it and wires the result by the pattern in its `README.md`. **No Electron imports.**
- `packages/host-install/` (`@volli/host-install`) — add a host over SSH (VC-700): the system-`ssh` runner (BatchMode, ControlMaster, fingerprint-surfaced host keys), the probe, the pinned-and-checksummed upload, the typed, resumable, provider-neutral provisioning step machine (`HostProvider`; SSH is the first adapter) and the `ssh -L` tunnel manager; its `/contract` entry is the JSON hostd's `install`/`start`/`enroll`/`devices`/`status --json` print. **No Electron imports.**
- `packages/agent-runtime/` (`@volli/agent-runtime`) — the product-owned executor boundary, Pi implementation, deterministic workspace/secret guards and host-API actor policy, prompt assembly, model access, and safe web tools.
- `packages/cli/` — the agent-facing `volli` CLI (built; Unix socket to main). App data lives under Electron's `userData` dir.
- `apps/hostd/` (`@volli/hostd`) — `volli-hostd`, the headless host: host-core with headless ports, serving the agent socket on Linux and macOS. **No Electron.** Packaging, health, shutdown and the systemd/launchd templates: its `README.md`.
- `packages/font-notices/` (`@volli/font-notices`) — the font license notices `apps/website` and `apps/docs` must publish beside the font binaries they redistribute (OFL-1.1 clause 2). `src/` is pure rendering — **no Electron/Node/DOM imports**, so each site resolves its own font package through its own bundler. `check-dist.mjs` (CLI: `check-font-notices`) re-reads the built `dist/` and fails the build on an uncovered font; it shares no code with the renderer so the two cannot agree with each other about a gap.
- `apps/desktop/src/renderer/lab/` — the UI lab (`pnpm lab`): browser-only scratches for trying interactions against real components/tokens with fixture data, before they become app features. Dev-server only, never built; imports the app, never the reverse. Its ordinary subject is UI state, UX flows and visual systems, with no main-process half or SQLite/Session-ledger reconciliation. The billing-aware model-choice eval is a narrow exception: explicit live classifier calls go through guarded, lab-mode-only Vite middleware in `apps/desktop/lab-server/`, with a browser-local eval log. This is not a product backend seam; credentials stay server-side and no lab code ships.

## Conventions

- A Session is durable and owns identity and ordered local history before any live executor attaches. The temporary native-adapter contract, processes, terminal panes, and UI views never own Session lifetime.
- Commands are explicit user intent. Persist intent before delivery; make acceptance idempotent and observable through durable receipts.
- Events are immutable facts. Local durable history is canonical; renderer stores project it into UI state and structured attention.
- **Session Events are exhaustive on write, tolerant on read.** Adding a kind must fail to compile until every writer handles it; reading durable history must never fail a whole Session over one kind this build no longer knows. History outlives the build that wrote it, so a category we can add but cannot retire is permanent by accident. Only an unrecognised `kind` is dropped — a malformed field inside a known kind is corruption and still fails loudly.
- The structured product has one target executor: `@volli/agent-runtime`, initially backed by Pi. Do not introduce SDK/ACP adapters, structured executor selection, capability parity work, or new provider-shaped product semantics.
- Resume, terminal recreation, and history navigation are distinct semantics.
- Retry transient transport failures without duplicating accepted work. Authentication, permissions, configuration, and quota failures require explicit user recovery.
- Existing hooks and terminal markers are compatibility evidence for TUI adapters, not the canonical source of Session truth.
- A Session starts with one root Agent Thread. Each Thread has at most one live Thread Binding; Conversation Branches and Generation Attempts preserve edits and regeneration without rewriting history.
- There is no adapter registry and no profiles: `SessionRuntime` holds one injected executor port. `adapterId` survives as a durable field for one job — telling a terminal companion attachment apart from the structured one — and is written by the runtime, never chosen by a caller. Terminals are explicit manual companions and never silent structured fallbacks.
- **A durable id derivation is frozen the moment it ships.** `session_events.id`, Attention ids and the transcript artifact digest are all re-derived from live data on every relaunch and deduped by exact string match, so changing how one is built does not error — it duplicates history, or leaves a row nothing can ever clear. Keep the old string, name the frozen segment, and say in a comment that it is durable rather than live.
- **Electron main is a host, not the product API.** New domain surfaces take command/projection shape with IPC as dumb transport; the standing boundary rules (durable ids, provisional ordering, JSON-safe payloads, receipts, no new raw IPC) are in `docs/BOUNDARIES.md`.

- Ticket rules + all auto-move logic: pure, tested TS in `@volli/shared`; the UI only observes it.
- Terminal access goes through the `TerminalEngine` seam: node-pty never leaves the host (host-core's terminal supervisor, `packages/host-core/src/pty`, driven by desktop's IPC adapter in `src/main/pty`), xterm.js (DOM renderer, no WebGL addon) never leaves the renderer's terminal components. The user's real Ghostty config stays the appearance source: the engine maps FROM it onto xterm's options and never invents a config language of its own. node-pty needs `pnpm -C apps/desktop run rebuild:native` after every install (the build desktop ships); it is N-API, so that build also loads under plain Node for host-core's tests. better-sqlite3 13 is N-API and ships its own cross-runtime prebuild, so the same command is a deliberate no-op for it.
- Domain data lives in SQLite at `<userData>/volli.db` behind `@volli/host-core` (`packages/host-core/src/db`); renderer stores hydrate at boot and write through semantic preload commands (`api.projects` / `api.tickets` / …). No product renderer-side persistence or localStorage; the dev-only billing eval log is not product state.
- Live terminals must never be unmounted incidentally (e.g. selecting a card) — session state is model-resident, views lazy.
- **Ship no third-party terminal themes.** Volli redistributes no Ghostty or iTerm2 color schemes. A terminal theme comes off the user's own machine (their Ghostty config and theme directories); the app's own fallback palette is derived from its design tokens (`renderer/src/terminal/appearance.ts`). `apps/desktop/scripts/check-vendored-themes.mjs` fails CI on vendored themes — excerpts included, since a sixteen-colour ANSI row lifted from someone's theme is the same redistribution as the whole file.
- **UI copy: let controls talk.** Settings and editors are not onboarding wizards. Do not add `description` on `SettingsSection`/`SettingsRow`, tutorial tooltips, or paragraphs under controls unless the user asked. Labels are nouns; the control is the explanation (pad, slider, segmented pill, origin chip). Rare exceptions only: irreversible confirms, one-line trust boundaries (e.g. Ghostty), blocked states with one recovery action. Module comments carry architecture; UI strings do not repeat them.
- **Color tokens are generated, not authored.** A **canvas** (a small set of positioned color stops plus vibrancy/grain, `packages/shared/src/theme/canvas/`) is what a scope stores; the whole token set — the app ladder, the veils and the on-canvas ink/shadow tiers — is derived from it at render time and written onto `document.documentElement`. **Appearance is resolved separately** (`light` / `dark` / `auto` against the system), so `class="dark"` is _not_ pinned: preload stamps the resolved mode before the first frame, from a `first-paint` hint main reads synchronously at window construction. Both are per scope — a workspace's canvas and appearance each override the global one independently, `null` meaning inherit. `globals.css` carries **two generated blocks**, `:root, :root.dark` and `:root.light`, between the BEGIN/END markers — **regenerate them together with `node apps/desktop/scripts/generate-theme-css.mjs`, never hand-tune them** (`--check` fails on stale), and add any new color token to `THEME_TOKEN_NAMES` (or `CANVAS_TOKEN_NAMES`) or it silently keeps that fallback forever. Never persist the _resolved_ token set; `{canvas, appearance}` is authoritative, and the `first-paint` row is not a counter-example — it holds one enum and one hex, the two values main cannot derive without a renderer, and nothing reads it once the renderer boots. Non-color tokens (radius, type scale, layout) are not themeable and stay hand-authored in `globals.css`; TS-consumable domain colors (project-tile palette) live in `@volli/shared`. Every product surface composes semantic generated tokens and treats materially different canvases in light and dark appearance as required compatibility targets; foreground/background pairs, interactive states, focus treatment, translucent materials, shadows, and overlays must retain their intended hierarchy and legibility across them. Spacing/width/type follow `docs/DESIGN.md` (five-step type scale, no arbitrary `text-[Npx]`; `<ContentColumn>` for Tier-A reading surfaces, `gutter` token for Tier-B workbench edges).
- Every context-menu action carries a neighboring Phosphor icon via the shared context-menu primitive.
- **Icon weight: interactivity determines fill, not a global standard.** Outline is the baseline — no prop. `fill` marks the one item that is the exception among its neighbours (the active one, or the one that went wrong), and only where background/ink/position are not already saying it; a scannable list is outline throughout except for its own exceptions. An explicit visual requirement may opt into `fill` locally through the shared primitive; it remains an exception, not a new baseline. Never reach for `fill` as generic emphasis: it is a _different drawing_, not a heavier one — 1.04×–7.61× regular's ink depending on whether the glyph has an interior to flood. `bold` is the real weight step (a flat 1.50×) and it is the small-size tier: at ≤12px regular draws lighter than its own label. Coverage is scale-invariant, so a bigger `size-*` can never fix a glyph that reads too thin — only `bold` can. `duotone`: never.
- Surface every failed mutation (alert/toast) — never silently swallow errors. **The one exception is work no one asked for**: a background refinement a person did not request (auto-titling's model call) has no failure a toast could ask them to act on, and its fallback is already on screen. Those log and keep the fallback. The test is whether a person is waiting on the result, not whether the code is async. **Errors are for operations that failed, not for outcomes the user chose.** A setting that produces a result we merely disagree with — a low-contrast canvas, a loud theme — is the user's decision: never a persistent warning, badge, or alert in Settings. If a choice genuinely deserves a caution, the control says it once at the moment of the choice and lets go. Likewise, diagnosis is our job, not the user's: a fault surface shows what is wrong and the one action that fixes it, and keeps the measurements (paths, PATH dumps, per-check evidence) in the support report rather than on the page.
- **The shipped licence notice is generated, not authored.** `apps/desktop/THIRD-PARTY-NOTICES` is derived from the resolved production dependency set (desktop + the bundled `volli` CLI, through deps, optional deps and required peers) by `node scripts/generate-third-party-notices.mjs` — a **root** script beside `check-workspace-licenses.mjs`, because it reasons about the whole workspace and the `.app` is only its first artifact. `electron-builder.yml` ships it and the root `LICENSE` into `Contents/Resources`. What the walk cannot see and the desktop owns — platform-native packages, build-time sources whose output ships, this app's vendored source, the editor-theme fragment — is a reviewed entry in `apps/desktop/notices/sources.json`. **Material another package vendored is declared by that package**, in its own `package.json` under `volli.notices`, naming the files it `covers` and the notice that covers them: material present with its notice absent is a hard failure, so coverage keys on files rather than on a grep for a marker. The copyright holder is read from the root `LICENSE`, never chosen here, and provenance nobody has established stays `unresolved` rather than guessed. Regenerate after any production dependency change; CI's `check:notices` fails on a stale notice, on packaging that stops shipping it, on a shipped package nothing covers, and on a shipped native package no entry pins.
- Ticket worktree branches: `volli/<DISPLAY-ID>-<slug>` (e.g. `volli/VC-12-mcp-server`).
- Changes go through branch + commit + PR — never commit directly to `main`. Strict TypeScript; no `any` at module boundaries.
- **Resolve clear in-scope issues.** Fix stale documentation, unsupported claims, and TODOs made answerable by the change. Report what changed. Ask only when ambiguity changes the work or an action is destructive, outward-facing, or otherwise needs authorization.

## Commands

- `pnpm dev` — full dev loop (renderer HMR + main/preload watch + Electron auto-relaunch). `pnpm run build` then `pnpm start` runs the built app.
- `pnpm lab` — the UI lab on :5174 (runs alongside `pnpm dev`); add an idea by dropping one file into `apps/desktop/src/renderer/lab/scratches/`.
- `pnpm typecheck` · `pnpm test` · `vp check` (= `vp fmt` + `vp lint`) — the quality stack. `pnpm typecheck` includes both the root TypeScript configuration and workspace packages; `vp` is the global toolchain CLI (Node/pnpm pinned in root `package.json`). `pnpm test` is the whole workspace suite — CI's job, not a pre-push step (see **CI is the gate** below).
- `vp run -r test:coverage` — **a separate gate, and CI runs it on every PR.** Holds `packages/shared`, host-core's protected host surface and a protected renderer surface at 100%; thresholds only evaluate under `--coverage`, so a green `vp run -r test` says nothing about it. CI shards the desktop suite and judges the thresholds once, over the merged coverage. A person can run it locally; an agent does not.
- `vp install` / `pnpm install` for deps; `pnpm run ensure:electron` (`apps/desktop`) prefetches Electron's lazily-fetched binary.
- Search with `rg` (ripgrep), not `grep -r` or `find -exec grep`. It honours `.gitignore`, so `node_modules/`, `coverage/` and build output stay out of results; `grep -r` drags generated coverage HTML back in as if it were source. `rg --files -g <glob>` replaces `find`, and `-uu` is the deliberate opt-in to ignored files. Where `command -v rg` finds nothing, fall back to `git grep -n` (tracked files only, so the same exclusions), or to `grep -rn --exclude-dir={node_modules,coverage,dist,out,.git}` outside a repository.
- CI: every PR runs Linux `Check + Build`, the desktop Vitest suite as `Test (desktop i/4)` shards, `Coverage (desktop)` (merges the shards and enforces the thresholds), `Test (packages)`, `N-1 compatibility` (the latest release, latest canary, PR's base, and fixed `v0.2.1` / `v0.2.2-canary.1` builds, run against a head-migrated profile; VC-633), and the macOS desktop smoke lanes; **`CI gate` is the one check that sums them**, and all must be green before shipping. **Desktop e2e smokes DO run in CI** — core e2e and the rest (sharded three ways, four-at-a-time) start together. The lane GLOBS `apps/desktop/e2e/*-smoke.mjs` and subtracts explicit credential/legacy exclusions plus measured quarantines in `apps/desktop/scripts/run-smokes.mjs`, so **a smoke you add runs in the same PR with no registration step**. A person can run the same thing on a dev Mac: `node apps/desktop/scripts/run-smokes.mjs` (add `--tier core` for core e2e, `--list` to see the selection). PRs touching only prose/website/docs skip the desktop lanes. `act pull_request --container-architecture linux/amd64` mirrors the Linux jobs locally, for a person debugging the workflow — not a pre-PR step. The Pi smokes stay local-only — they drive a live model turn, so they are structurally credential-gated and need `pnpm smoke:pi` with a display and a real `~/.pi/agent/auth.json`.

## CI is the gate

CI owns the full suite, every coverage threshold and the gating desktop smoke lanes. Local runs catch your own mistakes fast; they do not repeat CI.

**Core e2e** (`run-smokes.mjs --tier core`; `boot` is an alias) gates every desktop-relevant PR and runs after main merges: `board`, `composer-basics`, `terminal`, `worktree`, `agent-socket`, `session-rpc-transport`, `agent-cli-roundtrip`, `database-recovery`, and `canvas-theming` (`-smoke.mjs` filenames). The other non-quarantined journeys still gate PRs in the rest shards; new smokes join by default. A failure retries **once in a fresh profile**; retry-green is explicitly **FLAKY** in stdout, the job summary and 30-day both-attempt artifacts. Two failures or a native quiet-window violation remain red. `smoke-quarantine.yml` runs measured repeat flakers nightly with visible non-gating observations and one Backlog fix ticket each. Quarantine requires measured repeat failures, retained coverage, a tracked repair, and explicit return criteria. Smoke consolidation or deletion requires maintainer approval; this policy does not authorize deleting smoke coverage.

**This machine runs many Sessions at once**: a full local run slows every one of them, and then runs again on the PR anyway.

- **Local runs stay small.** Before pushing: `vp check`, the typecheck of each package you touched (`vp run --filter <package> typecheck`; `vp exec tsc --noEmit -p tsconfig.json` for the root config), and **only the test files you touched or that directly cover your change** (`vp test run path/to/file.test.ts`, from that package's directory). Changed a file on a protected coverage list? Check that one file, not the gate: `vp test run <its test file> --coverage --coverage.include=<the file, as that package's vite.config.ts lists it>` — the config's 100% thresholds then apply to it alone.
- **Never run a full workspace suite (`pnpm test`, `vp run -r test`), full coverage (`vp run -r test:coverage`) or the smoke matrix (`run-smokes.mjs`) locally** unless the ticket is specifically about those.
- **Push once, when the work is done** — not after every commit. Every push starts a fresh multi-minute run and cancels the one in flight.
- **Watching CI: never a `sleep` loop.** One blocking `gh pr checks <pr> --watch --fail-fast`, bounded by your shell tool's timeout or run in a background shell, then act on the result. On red, pull only the failing job's log (`gh run view <run-id> --log-failed`), fix just that, push once.
- **Hand off at PR-open.** Once the PR is open, move the ticket to review and name the PR; don't hold it in Doing waiting for green. If CI goes red later, fix it on the same branch.
- **Merge only on request, only on green.** Merge only when a maintainer explicitly requests it and `CI gate` is green on the PR's current head: `gh pr merge <pr> --merge --match-head-commit <sha>` (merge commits are this repo's method). No GitHub auto-merge — never arm `--auto`.
- **Red main rule.** The same CI step failing on two unrelated PRs is a `main` breakage: say so in the ticket, and don't try to fix it in your ticket's diff.

### Smoke quarantine requirements

Quarantine is an explicit, non-gating observation lane, not a way to suppress reds. Keep sole core coverage gating and preserve every assertion and graceful-shutdown requirement. A candidate needs at least 50 initial opportunities, confirmed recovery on at least three distinct SHAs, and a 95% Wilson lower bound above 2%. Count a retry-green or a genuine same-run/SHA rerun recovery once per initial opportunity; exclude related deterministic failures, speculative unrelated failures, and inherited rerun jobs. Track a repair and return condition. After fixing the root cause, restart the observation window and record at least 50 fresh-profile opportunities across three or more SHAs, including CI observations, with no FAIL/FLAKY before removing the quarantine entry. Exceptions require explicit maintainer approval.

Keep at most two fresh-profile processes per probe, never nested retries. Remove inherited `VOLLI_SMOKE_DIR` for both attempts; cancellation starts no retry. Runner jobs obey `min(requested jobs, VOLLI_CONCURRENCY_HINT)`. Statistical quarantine screening is descriptive, not a claim of independent or stationary failure probabilities. The complete retry and evidence contract is in [docs/development/smoke-tests.md](docs/development/smoke-tests.md). Retain both attempt logs, per-attempt exit code/signal, timing, lane, head SHA, workflow identity, and native quiet-window evidence. PASS is first-attempt green; FLAKY is fail-then-pass; FAIL and native-window violations remain red. Checkpoint incomplete runs as incomplete, never as passes. Keep CI artifacts for 30 days and save evidence outside the repository before expiration. Consolidation requires an old-assertion-to-new-journey mapping, preserved restart/isolation boundaries, and maintainer approval before deleting coverage.

## Session environment

Every Volli session — ticket or project, PTY or structured — starts with the same `PATH`: Volli's bin dir first, then the login shell's exported `PATH` merged with what the app already had. Do not discover tools by running them and reading command-not-found failures: run `volli identify` first. Its `env` block reports the resolved `PATH`, where each measured tool (`git`, `gh`, `node`, `npm`, `pnpm`, `yarn`, `bun`) resolves or that it does not, which of them this project actually implies (`env.requiredTools`: `git` for a repository, and for a JavaScript workspace the package manager its lockfile names plus the runtime that manager needs — `node` for npm/pnpm/yarn, nothing extra for bun, and never `gh`), and whether the workspace's dependencies are installed — in this repo, run `pnpm install` if they are absent. A structured Session does not have to ask about that last one: when its workspace has a package manifest and no installed dependencies, a first-message Turn Reminder says so and names the workspace's own lockfile-derived install command, so the first turn can simply run it. A tool that reports `-` but is not in `env.requiredTools` is one this project never runs, not a fault. `volli doctor` audits the same facts and names remedies. A tool that is installed but missing from `volli identify` is a `PATH` adoption failure, not a missing install: run `volli doctor --fix` first. It re-runs adoption for new Sessions and names what changed; the Session already running keeps its startup environment. If the tool remains absent, report it rather than working around it with absolute paths.

The `PATH` is built in two passes, and the `env` block reports each separately — a session that asked before the second one landed and a session that asked after do not have the same `PATH`, so one word could not describe both. `env.provenance` is the non-interactive pass, normally run at boot (`adopted` / `already-complete` / `probe-failed`). `env.interactiveProvenance` is the later pass, normally run once after the first window, which asks an _interactive_ login shell and picks up whatever the user's `.zshrc` exports — nvm, bun, rbenv, pyenv, mise. It reports the same three values, or `pending` before it has run. `volli doctor --fix` re-runs both passes and refreshes both fields. `pending` is not a failure: it means those toolchain directories may not be on the `PATH` yet. A repair affects only Sessions started after it; a Session already running keeps the environment it started with.

The same environment carries this Session's **parallelism budget**: `VOLLI_CONCURRENCY_HINT` is how many jobs this Session may assume it has — the machine's cores divided by the Sessions that were working when this one started. Volli writes it in the spellings common toolchains already read, so `cargo`, `make`, `cmake`, `go`, `pytest -n auto`, gradle and vitest self-limit with nothing asked of you: `CARGO_BUILD_JOBS`, `MAKEFLAGS`, `CMAKE_BUILD_PARALLEL_LEVEL`, `GOFLAGS`, `PYTEST_XDIST_AUTO_NUM_WORKERS`, `UV_THREADPOOL_SIZE`, `GRADLE_OPTS`, `VITEST_MAX_WORKERS`. Pass the hint by hand to anything that reads no environment — `jest --maxWorkers=$VOLLI_CONCURRENCY_HINT`, `xargs -P "$VOLLI_CONCURRENCY_HINT"`. A variable your own login shell exported is never overwritten: an exported `MAKEFLAGS=-j16` stays exactly as you set it. A budget only ever LOWERS a project's own cap, never raises it: in this repository `vitest.workers.ts` resolves `maxWorkers` as `min(2, VITEST_MAX_WORKERS)`, so a hint of 1 gives one worker and a hint of 8 still gives two. An explicit `--maxWorkers` flag outranks both — that is how CI, which has its runner to itself, takes every core (`--maxWorkers=$(nproc)` on each test job in `.github/workflows/ci.yml`), and how you take more for one deliberate invocation.

## Foundations

- **Data**: local SQLite (better-sqlite3, WAL, main-process-owned); transcripts as indexed files on disk. Local-first, single-player.
- **Terminal companions**: preserve the manifest registry, exact-hash trust, launch configuration, wrappers, hooks, CLI correlation, and honest terminal resume where they continue to improve manual terminal use. Preserve no generic structured-adapter machinery merely for future plurality.
- **Execution**: worktree-per-ticket. Terminal wrappers and hooks remain compatibility mechanisms for TUI harnesses.
- **Board**: fixed columns Backlog · Todo · Doing · Needs Review · Done. Explicit moves win over stale lifecycle evidence; automation only de-escalates and never destroys data. Archive worktrees instead of deleting them.

## Compatibility and public contributions

- **Frozen Sessions stay frozen.** A Session's birth `tool-surface` record and Code Mode declaration are immutable; never rewrite them for an existing Session. Within a warm-cache epoch, Agent Tool Surface declarations and the system prompt stay byte-identical. Additive refreshes are separately recorded durable facts that enter the provider surface only at a cold turn, compaction, or model switch. Code-Mode-only additions may arrive warm, announced in an appended message without changing the prefix. Reattachment restores the effective callable surface and last-cold declarations. Existing names are never removed or renamed; credentials never enter the durable shape. Preserve exact reattachment semantics (`packages/host-core/src/session-runtime/fixtures/main-surface-baseline.ts`).
- **N−1 compatibility is required.** Previous release, latest-canary, and base builds must still open compatible data and attach and replay Sessions. Name graceful degradation; never silently lose a tool, card, or frame. For 0.2.2, keep the fixed 0.2.1 and 0.2.2-canary.1 downgrade lanes alongside rolling tags. Add real-codec/transport compatibility tests whenever a change writes data older builds read. Assert behavior across any N−1 build, not an old build's exact decoded shape.
- **Migrations are expand-only and N−1-safe.** Preserve the compatibility floor (currently 58). Check the migration registry for the next available number; do not introduce a migration without a data requirement. Use expand → switch → contract for layout changes, and test older readers before contracting.
