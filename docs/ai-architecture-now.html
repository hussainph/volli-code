Where Volli is with AI

Volli is no longer a client for many coding harnesses. It has one structured AI experience: a durable Session that Volli owns, run by its own Agent Runtime, with Pi inside that runtime.

What is a Session, in plain terms?

A Session is the durable conversation and its local history. It exists before a live runtime attaches. It can survive a closed tab, an interrupted turn, or an app restart. A terminal pane is only a companion view; it is not the Session.

Read next: CONTEXT.md — Session, Command, Receipt, Attention; then packages/session-engine/src/session-runtime.ts.

Where does the AI actually run?

@volli/agent-runtime is the product boundary around Pi. It receives Volli-owned inputs: Session identity, workspace, model selection, Authority Snapshot, Runtime Brief, tool bundle, and a recovery reference. It emits Volli observations. Pi-specific detail stays inside this package.

Read next: runtime contracts; then Pi runtime implementation.

How does a message become durable history?

The user Command is recorded before delivery. Pi text deltas can appear immediately, but are only a transient overlay. A completed assistant message settles once into the Session ledger and a transcript artifact. This prevents a restart from duplicating a completed answer.

Read next: Session runtime — delivery, stream, and reconciliation; then SQLite ledger.

What does recovery mean here?

Volli's ledger is the source of truth. Pi keeps a recovery sidecar to restore model context and find entries after a restart. If the sidecar and ledger disagree, Volli raises Attention; it does not quietly trust Pi. An unfinished streaming tail is not treated as completed history.

Read next: Pi recovery and reconciliation; then desktop boot recovery.

Who owns model access and secrets?

Pi owns credentials and refresh. The renderer receives only a sanitized Model Access view: available models, account state, billing-source hint, and a recovery action. There is no silent model or account fallback.

Read next: Pi-to-Volli Model Access mapping; then sanitized RPC schema.

What stops an agent from doing unsafe work?

Each Session has an Authority Snapshot. Today, the Pi boundary enforces the Auto policy: execution is sandboxed, network and home-directory access are denied, and file tools stay in the Session workspace. Recent work also records a refused tool call as a durable fact. The richer escalation path—asking the user after repeated denials—is planned, not built.

Read next: authority plan — status and decisions; then authority gate and execution sandbox.

How does this reach the desktop UI?

Electron main hosts SQLite and the runtime. Session RPC is the narrow bridge over IPC. React has a resident chat client and store that project Session events into UI state. React does not parse Pi events, own recovery, or access secrets.

Read next: main composition; IPC bridge; renderer client.

What changed from the old architecture?

OpenCode is gone as a structured executor. Users select Model Access, not a harness or runtime profile. Old OpenCode history can remain readable, but Pi never resumes an OpenCode native conversation. Terminal tools remain useful manual companions; they are not a structured fallback.

Read next: Pi-native migration record — Session 7 and completion criteria.

Why do some files still say “adapter” or “harness”?

That is migration scaffolding inside the Session Engine, not a user-facing product choice. The desktop product attaches only Pi. The generic internal port also supports deterministic tests and the UI Lab for now. The next planned architecture cleanup is to collapse that port into the singular runtime shape.
