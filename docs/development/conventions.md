# Detailed conventions

The full text of conventions that `AGENTS.md` states in one line. Read the relevant section before touching that area.

## Store rule

**Store rule.** Today domain data lives in SQLite at `<userData>/volli.db` behind `@volli/host-core` (`packages/host-core/src/db`); renderer stores hydrate at boot and write through semantic preload commands (`api.projects` / `api.tickets` / …). No renderer-side persistence, no localStorage. Target: Convex is the store for board, Session and planning state as each area is ported. The board already reads and writes it in a **cloud launch** (flag on, signed in, a backend configured; main picks the store once per launch; a completed sign-in offers a restart into it and signing out restarts out of it): the window's own Convex client paints the Workspace's boards into the same renderer stores, which keep no state of their own, and writes go through Convex's optimistic updates computed by the shared `decide…` rules (a launch that cannot reach the backend shows, read-only, the last board it saw live, which main caches per account under `userData` and clears on sign-out), and a local launch is today's SQLite board; SQLite keeps runner-local machine state (Working copies, terminals, the Retry buffer, local credentials) and the **signed-out mode**, which remains supported and receives bug fixes only until Volli Local uses the same `convex/` functions on an embedded local backend. Local mode is permanent and free; cloud migration is optional, never a condition of continued local use. Don't add board or Session tables to SQLite for cloud work; new local tables hold machine state only.

## Terminal engine

Terminal access goes through the `TerminalEngine` seam: node-pty never leaves the host (host-core's terminal supervisor, `packages/host-core/src/pty`, driven by desktop's IPC adapter in `src/main/pty`), xterm.js (DOM renderer, no WebGL addon) never leaves the renderer's terminal components. The user's real Ghostty config stays the appearance source: the engine maps FROM it onto xterm's options and never invents a config language of its own. node-pty needs `pnpm -C apps/desktop run rebuild:native` after every install (the build desktop ships); it is N-API, so that build also loads under plain Node for host-core's tests. better-sqlite3 13 is N-API and ships its own cross-runtime prebuild, so the same command is a deliberate no-op for it.

## Color tokens

**Color tokens are generated, not authored.** A **canvas** (a small set of positioned color stops plus vibrancy/grain, `packages/shared/src/theme/canvas/`) is what a scope stores; the whole token set — the app ladder, the veils and the on-canvas ink/shadow tiers — is derived from it at render time and written onto `document.documentElement`. **Appearance is resolved separately** (`light` / `dark` / `auto` against the system), so `class="dark"` is _not_ pinned: preload stamps the resolved mode before the first frame, from a `first-paint` hint main reads synchronously at window construction. Both are per scope — a workspace's canvas and appearance each override the global one independently, `null` meaning inherit. `globals.css` carries **two generated blocks**, `:root, :root.dark` and `:root.light`, between the BEGIN/END markers — **regenerate them together with `node apps/desktop/scripts/generate-theme-css.mjs`, never hand-tune them** (`--check` fails on stale), and add any new color token to `THEME_TOKEN_NAMES` (or `CANVAS_TOKEN_NAMES`) or it silently keeps that fallback forever. Never persist the _resolved_ token set; `{canvas, appearance}` is authoritative, and the `first-paint` row is not a counter-example — it holds one enum and one hex, the two values main cannot derive without a renderer, and nothing reads it once the renderer boots. Non-color tokens (radius, type scale, layout) are not themeable and stay hand-authored in `globals.css`; TS-consumable domain colors (project-tile palette) live in `@volli/shared`. Every product surface composes semantic generated tokens and treats materially different canvases in light and dark appearance as required compatibility targets; foreground/background pairs, interactive states, focus treatment, translucent materials, shadows, and overlays must retain their intended hierarchy and legibility across them. The Settings window is the one approved exception: it paints generated system greys with the system accent (`paintSettingsCanvas`, `SETTINGS_CANVAS`/`SETTINGS_ACCENT_CANVAS`) in the resolved appearance, never the authored canvas, and renders every glass or floating material there opaque (VC-1228; `docs/DESIGN.md`). Spacing/width/type follow `docs/DESIGN.md` (five-step type scale, no arbitrary `text-[Npx]`; `<ContentColumn>` for Tier-A reading surfaces, `gutter` token for Tier-B workbench edges).

## Relational selectors

**A `:has()` on an element that holds the chat transcript makes every insertion restyle the transcript.** When a `:has()` argument reaches every descendant (`X:has(.y)`, Tailwind's `has-[.y]:`, `has-checked:`), Chromium flags the whole subtree; any element inserted in it then walks back up, and if a `:has()` sits left of a combinator on the way, Chromium restyles everything in the subtree that any such rule could select. One rule, `.chat-transcript:has(<scroll button>) …`, cost ~20 ms per streamed row at 1,200 rows (VC-1231). Write the argument with `>`/`+`/`~` (bounded to the depth written), or set a data attribute from the component that knows. `check:glass-design` runs `check-relational-selectors.mjs`, which fails on an unbounded `:has()` not listed with a reason in `relational-selector-allowlist.json`. Measure such costs on a fresh page load: deleting rules through CSSOM after render leaves Chromium's `:has()` flags behind and misattributes the cost.

## Icon weight

**Icon stroke: one shared outline family.** Import semantic symbols from `components/ui/icon.tsx`, never a vendor package at a call site. The seam uses only `@hugeicons/react` and the MIT `@hugeicons/core-free-icons` Stroke Rounded set. Its 24-unit drawing uses stroke 1.5 by default and 2.25 (1.5×) for ≤12px symbols or an explicit heavier stroke. Preserve the caller's size; enlarging a light drawing is not a weight step. A scannable list stays outline throughout. Mark its one active/error exception through accent/destructive ink or the existing selected background, not a fake fill. Pro, bulk, solid and `duotone` sets are forbidden. Provider/brand marks and identity tiles are separate from UI symbols and keep their own drawings. Every context-menu action carries a neighbouring symbol through the shared primitive.

## Errors and failure surfaces

Surface every failed mutation (alert/toast) — never silently swallow errors. **The one exception is work no one asked for**: a background refinement a person did not request (auto-titling's model call) has no failure a toast could ask them to act on, and its fallback is already on screen. Those log and keep the fallback. The test is whether a person is waiting on the result, not whether the code is async. **Errors are for operations that failed, not for outcomes the user chose.** A setting that produces a result we merely disagree with — a low-contrast canvas, a loud theme — is the user's decision: never a persistent warning, badge, or alert in Settings. If a choice genuinely deserves a caution, the control says it once at the moment of the choice and lets go. Likewise, diagnosis is our job, not the user's: a fault surface shows what is wrong and the one action that fixes it, and keeps the measurements (paths, PATH dumps, per-check evidence) in the support report rather than on the page.

## Third-party notices

**The shipped licence notice is generated, not authored.** `apps/desktop/THIRD-PARTY-NOTICES` is derived from the resolved production dependency set (desktop + the bundled `volli` CLI, through deps, optional deps and required peers) by `node scripts/generate-third-party-notices.mjs` — a **root** script beside `check-workspace-licenses.mjs`, because it reasons about the whole workspace and the `.app` is only its first artifact. `electron-builder.yml` ships it and the root `LICENSE` into `Contents/Resources`. What the walk cannot see and the desktop owns — platform-native packages, build-time sources whose output ships, this app's vendored source, the editor-theme fragment — is a reviewed entry in `apps/desktop/notices/sources.json`. **Material another package vendored is declared by that package**, in its own `package.json` under `volli.notices`, naming the files it `covers` and the notice that covers them: material present with its notice absent is a hard failure, so coverage keys on files rather than on a grep for a marker. The copyright holder is read from the root `LICENSE`, never chosen here, and provenance nobody has established stays `unresolved` rather than guessed. Regenerate after any production dependency change; CI's `check:notices` fails on a stale notice, on packaging that stops shipping it, on a shipped package nothing covers, and on a shipped native package no entry pins.

## Runtime executor slot

**Pi is the only agent loop**: `@volli/agent-runtime`, backed by Pi. Do not introduce SDK/ACP adapters, capability parity work, or new provider-shaped product semantics. The executor slot is a map that can hold more than one runtime (`SessionExecutorSlot`, `packages/session-engine/src/executor-slot.ts`, VC-916), so a Claude Agent SDK mode can come later; Pi is its only registered runtime and its default. Registering a second runtime, or giving a person or caller any way to choose one (a command, setting or UI), is its own owner-approved ticket. The Volli MCP tool server that mode also needs is separate 0.4 groundwork and is not built yet.

There are no profiles, and no caller picks a runtime: `SessionRuntime` holds the executor slot, keyed by each runtime's durable adapter `id`, and a Session runs on the runtime its newest attachment by a registered runtime recorded, else the slot's default. `adapterId` survives as a durable field — telling a terminal companion attachment apart from a structured one, and recording which runtime a Session is on — and is written by the runtime, never chosen by a caller. Terminals are explicit manual companions and never silent structured fallbacks.

## Frozen Sessions

**Frozen Sessions stay frozen.** A Session's birth `tool-surface` record and Code Mode declaration are immutable; never rewrite them for an existing Session. Within a warm-cache epoch, Agent Tool Surface declarations and the system prompt stay byte-identical. Additive refreshes are separately recorded durable facts that enter the provider surface only at a cold turn, compaction, or model switch. Code-Mode-only additions may arrive warm, announced in an appended message without changing the prefix. Reattachment restores the effective callable surface and last-cold declarations. Existing names are never removed or renamed; credentials never enter the durable shape. Preserve exact reattachment semantics (`packages/host-core/src/session-runtime/fixtures/main-surface-baseline.ts`).

## Experimental flags

**Experimental flags must preserve flag-off behavior.** Stable builds keep `cloud` off unless a fresh launch-time check grants the signed-in account preview access; storage and environment cannot bypass it. With it off, expose no cloud product surfaces (the stable Account pane is enrollment only). Host and runner services remain Electron-free, tenant-agnostic, and configured through ports and data rather than client-machine assumptions. Clients hold no durable facts the backend has not accepted (only a runner's Retry buffer may); credential enrollment and secret storage use provider-neutral ports.
