# Context-cache prefix survey

**Research date:** 2026-08-23
**Method:** Official provider documentation and first-party source only. This is a review aid for VC-164, not a measurement of a live provider cache hit.

## Provider baseline: Anthropic

Anthropic defines the cacheable request prefix in the order **tools → system → messages**. A change to an earlier item invalidates the cache after it; the tool-caching guide says a modified tool definition invalidates tools, system, and messages. Static material therefore belongs first, and a Session must not mutate its tool schema, ordering, prompt, or prior history. [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) · [Tool-use caching](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching)

The default cache TTL is five minutes, refreshed from the start of each read/write request; a one-hour TTL is available. Anthropic lists 5-minute writes at 1.25× base input price, one-hour writes at 2×, and reads at 0.1×. The benefit is therefore for overlapping or closely sequenced Sessions unless the caller deliberately buys longer retention. [Prompt caching—TTL and pricing](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

Observable evidence is `usage.cache_read_input_tokens` and cache-creation fields. Anthropic's beta cache diagnostics can additionally identify the first divergence as model, tools, system, or message history; it explicitly names a reordered tool and a timestamp interpolated into a system prompt as cache-invalidating examples. [Cache diagnostics](https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics)

## Security and correctness when facts move to messages

Moving volatile facts later protects the prefix; it does **not** make them less important to the agent. Claude's action and Gemini CLI both use the first user message/history entry, so the pattern is established, but it changes the failure modes:

- The first message must be product-owned and unambiguously delimited from user text. Otherwise a path, branch name, environment value, or brief content can blur a trusted runtime fact with untrusted task content.
- It must be delivered once to an empty history and persist in durable history. A reattach must not prepend a second, conflicting environment description.
- A fact whose correctness is security-critical or must outlive compaction cannot merely be a first-turn reminder. It needs an enforced tool boundary or a deliberate post-compaction delivery rule. A stale environment measurement should not be reissued as if current.
- Message placement cannot authorize a tool. The static authority/tool policy remains the enforcement boundary; changing a workspace path or ticket fact must not silently widen the available tool bundle.

These are correctness checks, not an argument to put volatile values back in the system prompt.

## Mapping to the VC-164 branch

The branch's `SystemPromptInput` is exactly Role, bundle, and resource set; product version is embodied by the composer code. Full Session identity, the Authority Snapshot, `workspacePath`, and `workspaceEnvironment` are outside that type. `composeFirstUserMessage()` carries the Runtime Brief and measured workspace reminder. `systemPromptSections()` is the single rendered/measured section list. The Pi attachment composes the system prompt and tools in `initialState`, prepends first-message material only when `agent.state.messages.length === 0`, and forwards Pi cache usage as `SanitizedUsage.cacheReadTokens` / `cacheWriteTokens`.

The desktop host now records the sanitized Agent Tool Surface—names and order only—as immutable Session input before attachment. Recovery reads that record, ignores newly enabled optional ports, and refuses to attach when a recorded capability can no longer be bound honestly. Credential values remain only in live provider closures and never enter durable Session data.

That matches the evidence above in three important ways:

1. It treats the cache prefix as **tool bytes plus system bytes**, rather than treating the prompt alone as cacheable.
2. It correctly treats Pi compaction as a standalone uncached utility call, while requiring the normal post-compaction chat to keep its tool array and system prompt.
3. It reports cache class as a claim about composition, not proof of a provider hit. The provider usage fields are the later falsifier.

## VC-164 review implications

### Merge blockers

1. **Wire-level invariant, not a constant-level invariant:** Review tests must record provider requests and prove byte-identical tool definitions (including order, schema, descriptions, and request controls that precede context) and system prompt on turn 1, later turns, and reattach. A name-only comparison is insufficient. This is required by Anthropic's tool-first prefix rule and supported by Codex's full request-property equality check.
2. **No session/turn fields can reach the system composer:** Different Session identity, Authority Snapshot, worktree path, Runtime Brief/ticket state, workspace measurement, date/clock, and model/attachment facts must leave `composeSystemPrompt()` byte-identical when Role, bundle, product version, and resource set are held constant. The type boundary must make those routes unavailable to the composer, not merely rely on a convention.
3. **Resource set must be part of the stated invariant:** Its order and contents are prompt bytes. Tests need both sides: different worktrees with the same resources produce the same prompt; a deliberately different resource set produces a different prompt. Do not promise cache sharing across different skills/index content.
4. **Compaction assertion must target the right request:** Do not require Pi's summary request to reuse the parent prefix. Require the first normal provider request after compaction to retain the same tools/system prompt and to start message context with summary plus retained tail, without rebuilding them into prompt bytes.
5. **Reminder integrity:** Review the first-message block for stable delimiters/order (Brief, then reminder, then caller text), exactly-once delivery, and an explicit test of the post-compaction outcome. If a reminder is intentionally elided after compaction, the test and comment must establish why the fact may become stale or is preserved by the summary.
6. **Every emitted `prompt.baseline` section has a cache class:** JSON and text output must include it, with message-side placement distinguishable from prefix placement. The reported total must include all first-message runtime material that is actually sent, while clearly excluding tool schema/provider overhead it cannot measure.

### Follow-ups / non-blockers

- **Cache telemetry (VC-87):** Validate classes against per-turn `cacheReadTokens` and `cacheWriteTokens`; report provider/model/TTL so a cache write after a supposedly shared start can be diagnosed instead of assumed to be a prompt defect.
- **Anthropic cache diagnostics:** Consider an opt-in debug capture of divergence reason when the provider supports it. It would identify whether a miss is tools, system, or history without logging prompt contents. This is beta provider functionality, not a VC-164 dependency.
- **Retention policy:** Choosing Pi's `PI_CACHE_RETENTION=long` / a one-hour TTL is an economic decision separate from prefix stability. Five-minute defaults limit cross-session benefits.
- **Tool discovery:** Anthropic supports deferred tool loading that appends tool references to conversation history without changing the prefix. Whether Volli should adopt an equivalent is future bundle design, not a reason to allow an existing Session's base tool array to drift.
- **Standing volatile constraints:** If a future reminder represents a durable safety/authority constraint rather than a first-command observation, design its replay after compaction (or enforce it outside prompt context) before using this first-turn pattern.
