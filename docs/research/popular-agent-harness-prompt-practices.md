# Popular Agent Harness Prompt Practices

*Research memo — 2026-08-09. “Prompt” below means publicly inspectable prompt assembly, instruction loading, and the enforcement boundary. It does **not** claim access to any vendor's unpublished base prompt.*

## Bottom line

The durable pattern is not a longer master prompt. It is a small, deterministic composition boundary: select only the instructions and tool descriptions applicable to this turn, record what was selected and why, then enforce authority in the runtime rather than in prose. Pi, OpenCode, Codex, Claude Code, Warp, and Aider take different routes to that split, but the strongest common lesson is: **prompt is behavioral guidance; the control plane owns authorization, containment, and durable proof.**

Volli is already unusually well positioned: [`composeSystemPrompt`](../../packages/agent-runtime/src/prompt.ts) is pure, ordered, and product-owned; it explicitly separates operating/trust/authority/workspace layers, treats repository and Ticket text as untrusted context, and emits a delimited Runtime Brief as the first user message. Its next conceptual opportunity is not ambient instruction discovery inside Pi, but prompt revision, recovery, and context provenance: preserve the exact composed prompt/resource set (or a content-addressed equivalent) that informed a turn, and distinguish it from a newly resolved context epoch on a later turn or recovery.

## Cross-harness patterns

1. **Layered, scoped context.** Global/user/project/path/task instructions solve different problems. Specific rules should refine broad rules under a documented order; they should not silently grant capability. A portable `AGENTS.md` is useful interoperability, but Volli's canonical product context should remain an explicit `TicketRuntimeSpec`, not whatever a substrate happens to discover.

2. **Progressive disclosure.** Skills, instructions, and repository context become liabilities when eagerly injected. Indexes, descriptions, path matching, hard byte/line limits, and lazy bodies preserve context for the task and improve traceability.

3. **Effective tools drive prompt revision.** Pi and Codex demonstrate that tool availability and tool instructions are part of agent behavior. A prompt that promises a stale tool is misleading; a runtime tool that exceeds its advertised bounds is unsafe. Rebuild or version the effective prompt whenever the permitted tool bundle materially changes.

4. **Modes are product semantics.** Aider's ask/code split and OpenCode's planning policy are useful only when the runtime makes the distinction observable and enforces it. For Volli, Command intent, Authority Snapshot, SessionInteraction, and receipts are stronger primitives than a provider-specific “mode.”

5. **Evidence at the boundary.** Provenance should include resolved instruction artifact, selector/path, digest or revision, prompt revision, authority snapshot, tool bundle, and model policy. Persisting this beside a committed turn/receipt permits faithful diagnosis without putting hidden provider reasoning into the Session ledger.

## Anti-patterns and caveats

- Do not treat repository instructions, Ticket prose, MCP content, tool output, or remote documents as authority. They are all potentially adversarial data. Volli's existing trust layer states this correctly; host-native containment and authority checks must continue to make it true.
- Do not over-centralize everything in a mutable `AGENTS.md` or gigantic base prompt. Long always-on instructions consume context, conflict, and reduce adherence; silent hierarchical merging makes recovery and review ambiguous.
- Do not rely on “plan mode,” tool descriptions, or read-only copy to block writes. The underlying capability must reject the action. Conversely, do not advertise tools/capabilities the runtime intentionally removed.
- Do not make “full autonomy” a hidden bypass of immutable deny policy. Warp documents such a bypass for its own per-task option; that is an operational choice, not a safety pattern to copy.
- Do not infer a vendor's confidential base prompt from behavior or third-party leaks. This memo uses only public docs and public source artifacts, and pinned source may differ from current upstream.

## Ranked implications for Volli's deterministic Pi boundary

1. **Preserve product ownership and determinism.** Keep discovery/resolution outside Pi. The current `TicketRuntimeSpec → prompt` seam is the right anti-ambient boundary and protects the Pi migration from importing provider-shaped product semantics.
2. **Make context provenance and prompt revision durable.** Treat each launch/turn/rebuild as a Context Epoch with a stable revision/digest and a manifest of resolved resources, selectors, and tool/authority/model inputs. Recovery can then replay the historical epoch or deliberately start a later one without rewriting history.
3. **Version prompt with capability changes.** If an Authority Snapshot, scoped tool bundle, or safety posture changes, it is an explicit Session event/action before the runtime receives a new effective prompt—not a silent reshaping of an in-flight Session.
4. **Use lazy, scoped resources without weakening trust.** Later product work can add skills or project conventions through a resolver that returns product-owned `PromptResource` values plus provenance. It should be bounded, path-aware, and selected before prompt composition; it should never let `process.env`, host configuration, or repository text expand tools or authority.
5. **Keep planning/review/mutation in Volli terms.** The durable record should be Command, authority decision, tool request/result, and receipt—not an opaque harness mode or a claim that the model followed its prompt.

These are design implications, not an implementation plan. The current boundary already captures the most important principle: a Session's authority and workspace are product facts, while Pi is an executor receiving a deliberately constructed view.
